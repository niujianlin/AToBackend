## P0 · 文档自相矛盾，必须先定一版

### 1. 多设备登录策略：到底踢不踢？

文档里同时存在两种表述：

- 通用业务规则 7：允许多设备同时登录，**新登录不会踢除旧设备会话**
- 约束与风险说明 2：用户登录时要新建 session，并**把该用户在该设备上的历史 session 全部置 revoked=1**

需确认：
- 踢除维度是 `device_id`（同设备重登踢旧的）还是 `platform`（同端互踢）？
- 同平台换了一台新设备（device_id 不同）要不要踢？
- 不同 platform（手机 + Web）是否永久共存？

> 这是整个多端设计的根，直接影响 `auth_session` 的写入与查询逻辑。

### 2. Token 刷新：原地更新 还是 新建+吊销？

文档内部三处冲突：

- 刷新流程核心规则 1：「生成全新 refresh_token，**原地更新 auth_session 单条记录**」
- 刷新接口边界逻辑 1：「**不新增 auth_session 行**，原地更新」
- 刷新接口边界逻辑 2（同页）：「每次刷新成功后**新建 session，老的 session revoke=1**」

另外，核心规则 3 要求「已使用过的旧 refresh_token 再次请求 → 判定泄露 → 全端踢下线」——**这与"原地更新"直接冲突**：原地更新后旧 token 记录已不存在，无法识别"旧 token 被复用"。

需确认：
- 采用 A（原地更新，实现简单，但**无法做重放检测**）还是 B（新建+吊销，可做检测，但 session 表增长快）？
- 若选 A，是否放弃泄露检测，或引入 redis 记录最近失效 token 的宽限期（如 30s）？

### 3. `user_id` 的语义与类型不统一

| 位置 | 定义 | 问题 |
| --- | --- | --- |
| `user_info.user_id` | `varchar(64)`，雪花/UUID | 对外业务 ID |
| `auth_credential.user_id` | `bigint`，注释写「关联 user_info.**id**（数据库主键）」 | 字段名与含义不一致 |
| `auth_session.user_id` | `bigint`，注释写「关联 user_info.id」 | 同上 |
| 登录响应示例 | `"user_id": 100001` | 数字，与 varchar 定义冲突 |
| 业务规则 4 | 「账号以 `user_inner_id` 作为内部主键，对外用 `user_id`」 | 引入了第三个名词 |

需确认：对外 `user_id` 是**雪花数字**还是**UUID 字符串**？内部关联统一走 `user_info.id`（bigint），并建议把两处 `bigint user_id` 改名为 `user_inner_id`。

### 4. 账号注销后，identifier 是否释放？

- 文档第 296 行自己写了「**原有 identifier 释放与否这里做方案说明**」——即明确未定
- 但同页又要求 `auth_credential.is_invalid=1`，防止注销后还用原第三方/手机号登录
- 而联合唯一索引 `uk_type_identifier(auth_type, identifier_hash)` 会**阻止**该手机号/unionid 被新账号绑定

需确认：
- 方案 A（永久占位）：注销手机号无法再注册，用户体验差但实现简单
- 方案 B（释放）：需要把 `is_invalid` 纳入唯一约束、或改用软删+部分索引、或在注销时把 identifier 改写为 `deleted_{id}_{hash}`

### 5. 短信验证码 `scene` 枚举不一致

- `/api/v1/auth/sms_code` 的 scene 枚举写：`login` / `bind` / `unbind`（换绑手机号）
- `/api/v1/auth/change_phone` 却要求 `scene=change_phone`，并说「新增场景，和 bind 隔离」

需统一为 `login` / `bind` / `change_phone`（或全用 unbind），否则 Redis key 规则对不上。

### 6. `bind` 接口字段名与安全模型

- 字段表：`phone_code`（短信验证码）；请求示例却写 `"code": "654321"`
- 字段表：`identifier` = openid / sub / 手机号
  - 但微信登录规则明确「**禁止使用 openid 做身份识别**，必须用 unionid」——bind 到底传哪个？
  - **前端直接传 identifier 存在安全风险**（可把别人的 unionid 绑到自己账号）

需确认：第三方绑定是否改为传 `auth_code` 由后端换取 unionid/sub？（推荐）

### 7. 登出接口鉴权自相矛盾

- 基本信息 + 边界逻辑：**二选一**，优先 Header，Header 失败再用 body 的 refresh_token
- 但 Headers 表把 `Authorization` 标为**必传**
- Body 表把 `refresh_token` 标为**必填**，示例却是空串 `""`
- 错误码 40106「Header 无 token，body 也没有 refresh_token」与「**无论是否找到有效会话都返回登出成功**」也轻微冲突

需确认最终规则：Authorization 与 body.refresh_token **至少一个**；两者都无 → 40106。

### 8. 设备列表接口的路径/方法/类型

- 路径写 `GET /api/v1/auth/session/list`，但**请求方式写 POST**
- `session_id` 表里是 bigint、响应示例是数字、revoke 接口的 body 示例却是 `"13900139000"`（手机号误粘贴）
- callout 要求「用 device_id 去重 + 过滤 revoked=1」——但若已在登录/刷新时踢掉同设备旧 session，**为什么还需要去重**？去重保留哪一条（最新 updated_at？）

### 9. 响应码体系混用

- `code` 类型标成 `string`，示例却是数字 `0`
- HTTP 语义码（`401`、`402`）与业务码（`40001`~`40073`、`40101`~`40106`）混用
- 登出成功示例 msg 是中文「登出成功」，其他接口是 `success`

需统一：HTTP 200 + 业务码（推荐），或严格 HTTP 语义码；`code` 类型固定为 int。

## P1 · 安全与稳定性缺口

### 10. access_token 能否被主动吊销？
文档只说「JWT，数据库不存」。那么用户点登出、被踢下线后，**access_token 在 2 小时有效期内依然可用**。
需确认：是否接受该窗口？还是要引入「每次请求校验 session.revoked」或 Redis 黑名单（jti 维度）？

同时缺失：JWT 签名算法（HS256/RS256）、claims 字段（是否含 `user_id`/`session_id`/`jti`）、密钥存放与轮换。

### 11. 敏感字段存储与密钥管理
- `refresh_token` 明文入库（varchar 255 + 唯一索引）→ 建议存 SHA-256 哈希，泄露不可直接使用
- `identifier` 用 AES-256-GCM 信封加密（密文每次不同，**无法等值查询**），所以查询依赖 `identifier_hash = HMAC-SHA256(...)`
- 缺失：AES 密钥与 HMAC 密钥的来源（KMS / 配置中心）、轮换方案、`identifier_hash` 是否加盐（不加盐易被彩虹表反查手机号）

### 12. 刷新接口并发竞态
App 端并发或网络重试会同时用同一 refresh_token 请求两次，按现规则第二次会被判定「token 泄露」→ **误踢用户全端下线**。
需确认：加分布式锁 / 行锁、或给旧 token 一个宽限窗口（如 30 秒内同 token 返回同一对结果，幂等）。

### 13. `sms_code` 接口缺风控
现仅「同手机号+场景 60 秒冷却」，**接口无鉴权**。
缺失：IP 维度限流、device 维度限流、验证码错误次数上限（防撞码）、图形验证码/人机校验、短信通道配额告警 → 否则可被短信轰炸。

### 14. 「账号状态校验优先级最高」会泄露账号存在性
规则说：无论凭证是否正确，账号被封禁/注销都返回「账号异常」。攻击者可借此枚举账号状态（配合 40004/40005 错误码）。
需确认是否调整为：**凭证校验通过后**再判账号状态。

### 15. AI 鉴权接口定义缺失
`/api/v1/auth/ai_verify` 只有流程图，没有说明：谁调用（客户端还是 AI 服务内部）、校验什么、为什么要返回 `session_id`、`is_valid=false` 与 401/402 的区别。错误码 `402` 也不符合本项目的业务码规范。

## P2 · 产品策略待确认

16. **手机号换绑不校验旧手机号**（文档已自认风险）：MVP 接受吗？是否加「设备二次确认」开关？
17. **手机号能否解绑**：「解绑第三方」章节写「有手机号时不允许解绑手机号」，又写「只剩最后一条凭证禁止解绑」，两条规则叠加后手机号是否**永远不可解绑**？

## P3 · 工程约定

22. **技术栈未定**：语言/框架（Java Spring Boot / Go / Node）、DB 版本（MySQL 5.7 or 8.0）、Redis 版本、部署形态。
23. **时区**：`datetime` 无时区，统一 UTC 还是 +08:00？响应时间格式 `2026‑10‑05 10:49:31`。
24. **`account_status=3` 与 `deleted_at`、`auth_credential.is_invalid` 三者职责重叠**，需明确以谁为准。
25. **对外 session_id 用自增 id 会暴露业务量**，建议改为 UUID/token。
26. **缺少「获取当前用户资料」接口**（PRD 的个人主页 / 我的页面需要）。
27. **错误码汇总表**：当前散落在各接口（40001-40073、40101-40106、401/402），需统一收敛成一份全量错误码字典。
28. **日志与审计**：登录成功/失败、踢设备、绑定/解绑、注销、换绑均需留痕；敏感字段（手机号、token）需脱敏。
